# Chordlab

An offline-first, installable chord laboratory: explore chords on piano, guitar and ukulele, write songs with chords right in the lyrics, and run setlists on stage.

**This project has no subfolders.** Every file sits in one folder so it uploads to GitHub in one go. File names carry their old folder as a prefix, so related files sort together (`music-chords-parse.ts`, `storage-backup.ts`, `app-Songs.tsx`).

## Run
```bash
npm install
npm run dev      # development
npm test         # 200+ tests
npm run build    # type-check + production build into dist/
npm run site     # build, then copy the finished website into this folder (see "Publishing")
```

## Files, by prefix
| Prefix | What it is |
|---|---|
| `music-*` | pure music theory, no React: notes, intervals, chords (including `music-chords-parse.ts` and `music-chords-identification.ts`), scales, theory |
| `instruments-*` | instrument views and `instruments-stringed-shapes.ts`, the fingering search |
| `search-engine.ts` | the search ranking and chord matching (pure, tested) |
| `saved-shapes.ts`, `app-useSavedShapes.ts` | saved-shape rules (which shapes belong to which chord, rename-instead-of-duplicate) and the hook the fretboard uses |
| `songs-*`, `setlists-*` | data types and logic (chord-sheet parser, line layout, setlist operations, performance view data) |
| `storage-*` | IndexedDB, repositories, versioned migrations, backup/import |
| `playback-*` | Web Audio engine |
| `app-*` | screens and components (`app-Songs.tsx`, `app-Setlists.tsx`, `app-PerformanceMode.tsx`, ...) and `app-styles.css` |
| `*.test.ts(x)` | tests |
| `app.html`, `main.tsx` | the source entry point of the app |
| `index.html`, `app.js`, `app.css`, `sw.js` | **the built website** (generated by `npm run site`; don't edit by hand) |
| `sw-template.js` | source of `sw.js`; the build stamps it with a version and the list of files to cache |
| `manifest.webmanifest`, `icon-*.png` | PWA files |
| `publish-site.mjs` | copies the build into this folder |

Barrel files are named after their old folder: `music-chords.ts` re-exports everything in `music-chords-*.ts`. To change the database, add a numbered entry to `MIGRATIONS` in `storage-db.ts`; never edit an old one.

## Publishing on GitHub Pages (no build step, no workflow)
The finished website is committed right next to the source: `index.html`, `app.js`, `app.css` and `sw.js` in the repository root. GitHub Pages only has to serve those files.

1. Create a repository and use **Add file → Upload files**. Upload **every** file from this folder (not `node_modules`; there is no `dist` folder). Files with the same name are replaced.
2. **Settings → Pages → Build and deployment → Source: Deploy from a branch**, branch `main`, folder `/ (root)`. Save.
3. After about a minute the site is at `https://YOUR-NAME.github.io/REPOSITORY-NAME/`.
4. Open it once while online and use *Add to Home screen*. After that it opens offline. When you upload a new version, the app shows an "Update now" banner.

**Every update: upload all the files again**, including `index.html`, `app.js`, `app.css` and `sw.js`. Those four are the app itself. If you upload only the source files, the site keeps showing the old version.

## Blank white page, or "Chordlab didn't start"
A browser can't run the source files (`main.tsx`); it runs the built ones. A white page almost always means `index.html` in the repository is the *source* page rather than the built one, or `app.js` / `app.css` are missing.
- Check that the repository root contains `index.html`, `app.js`, `app.css` and `sw.js`, and that `index.html` mentions `app.js` (open it on GitHub and look).
- Re-upload all files from the latest zip, wait a minute, close the tab and reopen the site.
- Still stuck: open the site, then Chrome menu → **Settings → Site settings → Storage → Clear data** for that site, and reload.

If you have a computer: `npm install`, then `npm run site` rebuilds the four files for you.

## Notes
- `sw-template.js` carries two placeholders that the build fills in (a version, and the list of files to cache). Don't remove them. See `vite.config.ts`.
- Built files have fixed names (`app.js`, `app.css`) so an upload replaces the old ones; the service worker fetches fresh copies on every release.
- A setlist slot stores a semitone `transpose`; Performance Mode transposes chord symbols on the fly, so the song itself is never changed.
- The song editor stores chords as symbols (`F#m7/A`), not as references, so songs survive reloads and engine changes.
